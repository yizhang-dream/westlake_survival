# 凭据多来源不一致：为什么一台机器会「长期一直报密码错」

**日期**：2026-10-27　**背景**：本机 keyring 存了 8 位学号（配 10 位密码），
明文文件存的是正确的 11 位学号（配 9 位密码），两个不同账号；keyring 优先级高，
于是每次登录都用错号，一律报 `IAM 4020 用户名或密码错误`。

## 一、读取优先级（`sso/creds.py:read_credentials`）

```
内存(cred_set) → 环境变量 WESTLAKE_CREDENTIALS → keyring → ~/.westlake_survival/credentials.txt
```

**先命中即返回，全程不比对、不告警。** 这就是问题的结构性根源：高优先级来源一旦
存了别的账号或旧密码，低优先级那份**永远读不到**，也不会有任何提示。

设计上唯一的安全网是：keyring 若「指针在但密码项缺失」，`read_credentials_keyring`
返回 `None` 并回退文件——半写入不会造成长期错误。但**完整写入的旧凭据**没有这层保护。

## 二、新机器上会不会长期错：逐场景

| # | 新机器状态 | 结果 | 是否长期错 |
| --- | --- | --- | --- |
| 1 | 干净机器，无任何凭据 | `AuthError`「未配置」+ 引导 → `setup` | 否，报错语义正确 |
| 2 | 有 keyring 后端但无条目 | 回退配置文件 | 否 |
| 3 | keyring 不可用（Linux 无 Secret Service、未装 `[secure]`） | 读取异常 → 返回 None → 回退文件 | 否 |
| 4 | keyring 存旧账号/旧密码，文件是新的 | **keyring 静默胜出，文件永不生效** | **是** |
| 5 | 环境变量 `WESTLAKE_CREDENTIALS` 留在 shell profile 里且已过时 | **env 优先级最高，永久胜出** | **是** |
| 6 | 从别的机器拷来 `credentials.txt`，本机 keyring 另有条目 | 拷贝的文件不生效，用的还是本机旧号 | **是** |
| 7 | 改密码后只用 `WESTLAKE_NO_KEYRING=1` 或 `setup --no-keyring` 重配 | 只写文件，旧 keyring 原封不动 → 默认路径继续错 | **是（最阴）** |

场景 4–7 的共同形态：**「修」的动作本身没有碰到真正生效的那一份**。
场景 7 尤其隐蔽——`WESTLAKE_NO_KEYRING=1` 本是测试隔离用的绕过手段，被当成
「临时解决办法」反复使用，反而让旧值一直留在最高优先级上。

## 三、为什么是「长期」而不是「一次」

三个自我强化环：

1. **错误信息指向错方向**：报「用户名或密码错误」，用户自然去核对/重输密码。
2. **`status` 无法分辨**：旧版只报「keyring：有 / 配置文件：有」，两份都"有"看起来健康。
3. **重试触发验证码锁**：反复试密码累积 IAM 失败计数 → 强制图形验证码（实测 14h+ 不复位，
   成功登录也不复位），期间无头登录全废。用户于是更确信"密码错/工具坏"。

三条叠加，一台机器可以稳定地错上几天，且每天都"再试一次"续期。

## 四、已落地的防护（2026-10-27）

| 能力 | 行为 |
| --- | --- |
| `westlake sso creds status` | 列出**各来源学号（脱敏，前 3 位 + 位数）**；两处不同账号或同号不同密码时直接告警，并给修复命令 |
| `westlake sso creds sync-keyring` | 把配置文件的凭据写进钥匙串，一键修好「keyring 存旧号」 |
| `westlake sso login` 失败 | 先检查来源一致性并提示，再抛原始错误——把"先怀疑密码"改成"先排除来源冲突" |
| `westlake setup` 只写文件时 | 若钥匙串里另有凭据，明确告警「本次配置不会生效」 |

判定逻辑只看两件事：学号是否相同、密码是否相同（长度不同即判不一致），**不打印密码**。

## 五、新机器的正确姿势

1. 配一次：`westlake go` → `/setup`，或 `westlake setup`（默认写 keyring）。
2. 验收：`westlake sso creds status` —— 应只看到一个来源「有」，或两处学号完全一致。
3. 有告警就 `westlake sso creds sync-keyring`，不要用 `WESTLAKE_NO_KEYRING=1` 长期兜底。
4. 改密码后重跑 `setup`（两条路径会一起更新）；只改文件不改 keyring 必然复发。

## 六、仍然存在的边界（如实记录）

- 环境变量来源**无法自动纠正**：`WESTLAKE_CREDENTIALS` 写在 shell profile 里时，
  工具只能告警，改与不改由用户决定。
- 密码不同但长度相同时不会被判为不一致（本工具不存明文哈希比对，避免额外暴露面）。
  这类情况仍要靠 `setup` 重配一次来收敛。
